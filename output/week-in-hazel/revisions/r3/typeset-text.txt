A cramped chip gets a room of its own. Modules, all the way up.

Alexander Bandukwala has built a nine-part staircase from real module values to a modular standard library. The higher floors are explicitly provisional.

A READING MAP, NOT NINE INDEPENDENT FEATURES

Try the language on itself

Modular implicits + a modular standard library

#2508  #2510

The useful shift: a module becomes a value with a signature, rather than a dressed-up labeled tuple. Width matching lets a richer module satisfy a smaller interface where an expected type is given. Abstract members give names such as M.T a meaningful boundary.For example, a greeting function that asks only for name : String can accept a module containing both a name and an age. The narrower interface hides the extra member. Callers can add information without rebuilding a tiny module just to fit the function.

That generosity has a boundary. Differently shaped modules in the two arms of an if do not silently acquire a common interface; the author must write the narrowing ascription. The place where information disappears stays visible in the source.Upstairs, implicit module arguments and List.map-style names ask how the language feels using its own machinery. Parts 8 and 9 say they are not close to done. Sharing constraints, implicit-design questions and unmeasured library costs remain part of the story.

Andrew’s modular editors let a definition occupy the editing surface while its program supplies context, results and tests. A recent fix makes edits beyond the first definition feed whole-program evaluation.The screenshot is a small desk inside a large room: RunningSums.running_sum, lifted out of Mega 1k. Its accumulator builds partial sums in reverse order, then reverses the list. The probe exposes an intermediate total; the result below still belongs to the surrounding program.

That distinction matters for an assistant too. Selecting a smaller piece should not mean silently changing the world in which it runs. The open agent-hardening PR makes probe requests wait for evaluation to settle, bounded at roughly ten seconds. Otherwise an assistant may inspect a value before its latest work has finished.The canvas stack brings these ideas together: a graph to find the work, a definition-sized editor to do it, and observations that still refer to the whole document. The next page shows the map running locally.

A useful test of the idea: pick a definition, inspect a live sample, then return to the whole program. The interfaces must agree about which document the value came from.

OPEN PR / FUMOLA LIVELITS / EXPERIMENTAL

Two languages.One notebook.

A staged, running example on fumola-livelit-mvp: Fumola calculates a GCD and reads a named cell; Hazel receives (6, 42). The shot shows the bridge working. It does not measure incremental reuse.

M

Matthew Hammer's Fumola integration puts a foreign runtime inside a Hazel document. The interesting boundary is ownership: the livelit carries a name for state that lives elsewhere. Sharing an instance can mean sharing its store and history. Copying or reloading the document raises questions an ordinary slider never had to answer.

The branch has already outgrown its original two-widget PR description: its current documentation names four livelits. The interface is still moving.Two loader PRs merged this week, both into the Fumola feature branch. They add source fallback and content-addressed loading, plus a way to identify the runtime that actually loaded.

Small infrastructure, large consequence. The runtime lives outside Hazel's repo and can change independently. The branch's runtime notes explicitly identify gaps in live integration testing. A content hash makes a surprise version diagnosable; it does not make the dependency pinned.
