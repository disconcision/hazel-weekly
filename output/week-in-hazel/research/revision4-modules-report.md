The other seven PRs are #2494, #2495, #2498, #2500, #2501, #2503 and #2508.

2. **Signatures and modules become distinct language constructs; member binding also gets a practical fix.** Part 1 removes the labeled-tuple interpretation, evaluates module items sequentially, and resolves member projections by name. Its follow-up fixes `let f(x) = ...` inside a module: the old binder calculation exported `x`, rather than `f`. The draft also improves missing-member diagnostics and qualified completions. Source: [#2493, Statics, Dynamics and Follow-up commits](https://github.com/hazelgrove/hazel/pull/2493).

3. **Width matching means a function can ask for a smaller interface, at explicitly typed positions.** A greeting function requiring `{ let name : String }` can accept a module that also contains `age`; the function's binder exposes only `name`. Annotations, ascriptions and typed arguments support this matching. Differently shaped `if` arms do not silently join at a shared signature: the author must explicitly ascribe the wider arm. Labeled tuples do not gain width subtyping, and a list of wider modules is not automatically a list of narrower signatures; ascribing each element is the stated workaround. Source: [#2494, Motivation, What it deliberately does not do, and Known gap](https://github.com/hazelgrove/hazel/pull/2494).

4. **Abstract type members hide a representation while retaining a usable identity.** A signature can declare `type T` without defining it. A module must supply its definition, but outside an ascribed module `M`, `M.x` has type `M.T`. Aliasing `M` preserves that identity; independently sealing two modules produces distinct types. Part 4 prevents a type rooted at a local module parameter from silently turning into unknown after leaving scope, and makes escaping identities fresh per application. Ordinary explicit module parameters still lack a way to preserve the caller's type equation. Sources: [abstract types and path identity, #2495](https://github.com/hazelgrove/hazel/pull/2495), [module functions and generative escape, #2498](https://github.com/hazelgrove/hazel/pull/2498).

5. **Parts 5–7 make errors more local and distinguish interface declarations from implementation shadowing.** A missing tuple label is marked at the label; signature mismatches name missing members on variables and function arguments; CLI carets cover the diagnosed term. Inner modules receive the outer signature's expectations, allowing errors to point at the faulty inner definition. A repeated signature member marks the later declaration, while repeated bindings in a module body still shadow normally. Value/module members share one namespace, with type members separate. Sources: [#2500](https://github.com/hazelgrove/hazel/pull/2500), [#2501](https://github.com/hazelgrove/hazel/pull/2501), [#2503](https://github.com/hazelgrove/hazel/pull/2503).

6. **The implicit-argument prototype performs ordinary argument insertion after type-directed selection.** A function may take `(implicit S : SHOW, x : S.T)`; `show(3)` can then select a marked integer instance and elaborate to a call such as `show(ShowInt, 3)`. Only explicitly marked instances participate. No suitable instance or several suitable instances produces a mark at the application, with a hole supplied so evaluation can continue around the error. The PR explicitly expects the syntax, selection rule and error reporting to change. Unknown types can make candidates ambiguous, and there is no recursive instance search to derive a list instance from an element instance. Source: [#2508, example, What it does, and Known gaps](https://github.com/hazelgrove/hazel/pull/2508).

7. **The standard-library prototype adds qualified access without renaming existing programs' functions.** It groups existing functions under `List`, `String`, `Int`, `Float`, `Option` and `Pair`; flat names remain and refer to the same implementations. `SHOW` and `ORD` are supplied with base-type instances, but a program must explicitly opt each instance into resolution. The draft warns that every `List.map` mention copies a 65-member module and says the cost has not been benchmarked. Sources: [#2510, What it does, decisions, and Known gaps](https://github.com/hazelgrove/hazel/pull/2510), [tracked BuiltinsModules.re at 9dd7911](https://github.com/hazelgrove/hazel/blob/9dd7911bdb0846613eef4f31543e378855c5e68a/src/language/builtins/BuiltinsModules.re). The newer #2498 body says those two defects, plus non-idempotent parentheses printing, now have fixes and deterministic tests in that draft. #2510's closing test warning still describes the first two as expected failures. ## Suggested feature copy

### Modules II: interfaces you can pass to a function

Alexander Bandukwala's nine-part draft stack turns modules into first-class values with signature types. A module can be passed to a function, returned from one, or checked against an interface that hides implementation details. The changes also repair some basic member behavior: a function written as `let f(x) = ...` inside a module previously exported `x` instead of `f`. Part 1 corrects that binding.

A greeting function makes the interface rule concrete. If it asks for a module containing `name : String`, a caller can supply both a name and an age. The function sees the smaller signature, so it cannot reach `age`. This matching applies where an expected type is supplied. It does not automatically reconcile differently shaped modules in the arms of an `if`; that requires an explicit ascription on the wider branch.

Abstract members add a second kind of hiding. A signature can declare `type T` while the implementation defines `T = Int`. Outside a sealed module `M`, its exported value has type `M.T`, keeping clients from treating it as an integer. An alias of `M` preserves that identity; a separately sealed module has its own. Part 4 also prevents a local module's abstract type from silently becoming unknown when it escapes the module's scope.

The middle PRs improve what happens when a program gets these rules wrong. Missing members are named, nested signature expectations reach the inner definition, and a duplicate interface declaration is marked at the second occurrence. Repeating a binding inside the implementation still means ordinary shadowing. These are small distinctions, but they affect where a programmer has to look to repair a program.

Parts 8 and 9 are explicitly unfinished prototypes. The implicit-argument experiment lets `show(3)` select an integer-formatting module from the marked instances in scope; the elaborated call passes that module as an ordinary argument. Unknown types can make selection ambiguous, and there is no recursive search to build, for example, a list formatter from an element formatter.

The library experiment supplies `List`, `String`, `Int`, `Float`, `Option` and `Pair`, alongside the existing flat names. `String.length` and `string_length` reach the same implementation, so existing programs keep working. The outstanding performance question is specific: mentioning `List.map` currently copies a 65-member module, and that cost has not been measured. Both prototypes are there to expose design choices and costs before a merge; none of this stack had landed at the issue's cutoff.
